# Теория индексов PostgreSQL — GuitarMatch IS

## pg_stat_user_indexes: idx_scan, idx_tup_read, idx_tup_fetch

Три счётчика, которые PostgreSQL накапливает с момента последнего `pg_stat_reset()`:

- **`idx_scan`** — сколько раз планировщик обращался к индексу. Если 0 — индекс ни разу не использовался.
- **`idx_tup_read`** — сколько записей индекса было прочитано (из самого B-tree/GIN, до обращения к heap).
- **`idx_tup_fetch`** — сколько строк реально достали из heap. Меньше `idx_tup_read`, если часть записей отсеялась: MVCC (мёртвые версии строк видимы в индексе, но уже удалены в heap) или Bitmap Scan (сначала строится битмап, потом heap-fetch только нужных страниц).

`idx_tup_fetch` полезен для детектирования Index-Only Scan: если индекс покрывает все нужные колонки, PostgreSQL берёт данные прямо из него, не идя в heap — тогда `idx_tup_read` большое, а `idx_tup_fetch` близко к 0. В остальных случаях для анализа достаточно `idx_scan` и `idx_tup_read`.

## pg_stats: n_distinct, null_frac, avg_width

Статистика, которую PostgreSQL собирает через `ANALYZE` и использует для выбора плана:

- **`n_distinct`** — оценка количества уникальных значений. Положительное число — абсолютное (`990` уникальных значений), отрицательное — доля от числа строк (`-0.49` означает ~49% уникальных, `-1` — все значения уникальны).
- **`null_frac`** — доля строк со значением NULL. `0.5` = 50% строк.
- **`avg_width`** — средний размер значения в байтах.

**Как это применяется при анализе индексов:**

`n_distinct` показывает selectivity. Чем ближе к `-1`, тем хуже B-tree для equality-фильтрации — каждый запрос возвращает максимум одну строку, но если таких запросов нет, индекс просто занимает место. Так обоснованы удаления `idx_product_description` и `idx_shop_address`: `n_distinct = -1` при полном отсутствии equality-запросов.

`null_frac` обосновывает partial index. Если 50% строк — NULL, полный индекс содержит 50% бесполезных записей. Partial index `WHERE product_id IS NOT NULL` сразу вдвое меньше — это прямо из `null_frac = 0.5` для `feedback.product_id`.

`avg_width` полезен при ручном подсчёте размера индекса (`n_distinct × avg_width × коэффициент`), но когда реальные размеры доступны через `pg_stat_user_indexes.size`, он вторичен.

## Чтение EXPLAIN ANALYZE

`EXPLAIN (ANALYZE, BUFFERS)` выполняет запрос реально и показывает фактические метрики рядом с плановыми:

- **`actual time=X..Y`** — время в мс от старта узла (X) до выдачи последней строки (Y)
- **`rows=N`** — фактическое число строк, выданных узлом
- **`loops=N`** — сколько раз узел был выполнен; реальное время = `actual time × loops`
- **`Buffers: shared hit=X read=Y`** — X блоков из shared_buffers (RAM), Y — прочитано с диска (дорогостоящие I/O-операции)
- **`Rows Removed by Filter: N`** — строки, прочитанные индексом/сканом, но отброшенные фильтром после

**Ключевые типы сканирования:**

| Тип | Когда применяется | Стоимость |
|---|---|---|
| Seq Scan | Таблица мала или selectivity низкая (>5-10% строк) | O(N страниц) |
| Index Scan | Высокая selectivity, нужны данные из heap | O(log N + K heap fetches) |
| Index Only Scan | Индекс покрывает все нужные колонки (INCLUDE или partial) | O(log N + K), без heap |
| Bitmap Index Scan | Средняя selectivity или несколько условий через OR/AND | O(log N) → Bitmap Heap Scan |

Ключевой сигнал неэффективности — большой `Rows Removed by Filter`: это строки, которые были прочитаны из индекса или heap, но отброшены предикатом. Хороший индекс сводит это число к минимуму.

## Selectivity и почему Boolean/enum плохо работает с B-tree без partial-индекса

**Selectivity** — доля строк таблицы, проходящих условие фильтра: `selectivity = matching_rows / total_rows`.

Планировщик выбирает Index Scan только если оценочная selectivity ниже ~5-10%. Если запрос `WHERE available = TRUE` отбирает 80% строк, планировщик предпочтёт Seq Scan — чтение каждой записи индекса плюс heap fetch обойдётся дороже, чем один линейный проход.

**Почему стандартные B-tree индексы плохи для Boolean и enum-колонок:**
- **Boolean** (`available`, `accepted`): два возможных значения. Если 80% строк `available = TRUE`, то индекс по `available` имеет selectivity 0.8 — планировщик его проигнорирует.
- **Enum с малым числом значений** (`type_of_product`: ~10 типов): selectivity ~10-20%. Одиночный B-tree пограничен; composite index `(type_of_product, avg_price, rate)` резко повышает selectivity за счёт пересечения условий.

**Как partial index решает проблему:**

Partial index индексирует только подмножество строк, удовлетворяющих предикату. При запросе `WHERE product_id IS NOT NULL AND product_id = 3` PostgreSQL работает с индексом, который уже содержит только не-NULL строки — selectivity внутри индекса = 100% (каждая запись индекса удовлетворяет условию). Плюсы:
- Размер индекса в 2-10× меньше → меньше I/O при каждом сканировании
- Планировщик увереннее выбирает Index Scan, зная что индекс компактен

## Write overhead

Каждый `INSERT`, `UPDATE`, `DELETE` требует обновления всех индексов на затронутые строки. Для таблиц с высокой частотой записи это критично:

- **Стандартный индекс**: обновляется при любом изменении строки, где индексированная колонка присутствует (даже при HOT update PostgreSQL обновляет индексные страницы если изменилась индексированная колонка).
- **Partial index**: обновляется **только** при изменении строк, входящих в предикат. `INSERT` с `available = FALSE` не пишет в `idx_shop_product_available_product_price` вообще.
- **Composite index**: один индекс покрывает несколько колонок — одна запись вместо трёх отдельных индексов. Write overhead ниже, чем у трёх монолитных индексов суммарно.

## Почему LIKE '%...%' не работает с B-tree

B-tree индекс организован как упорядоченное дерево по значению ключа — поиск эффективен только по левому префиксу. Запрос `WHERE name LIKE 'guitar%'` может использовать B-tree: он эквивалентен `name >= 'guitar' AND name < 'guitars'`. Но запрос `WHERE name LIKE '%guitar%'` содержит **ведущий wildcard** — неизвестно, с какого листа дерева начинать обход. PostgreSQL вынужден выполнить Seq Scan по всей таблице.

Это затрагивает три места в GuitarMatch IS:

```java
// ProductSpecification.java
criteriaBuilder.like(root.get("name"), "%" + name + "%")
// → WHERE name LIKE '%...%' → Seq Scan на 130k строк

// MusicianRepository.java
List<Musician> findAllByNameContains(String name)
// → WHERE name LIKE '%...%' → Seq Scan на 1.3k строк

// ArticleRepository.java
Page<Article> findByHeaderContaining(String header, Pageable pageable)
// → WHERE header LIKE '%...%' → Seq Scan
```

## Как работает trigram (pg_trgm)

**Триграмма** — набор из 3 последовательных символов. Строка разбивается с добавлением двух пробелов слева и одного справа:

```
"guitar" → {"  g", " gu", "gui", "uit", "ita", "tar", "ar "}
```

**GIN-индекс** (Generalized Inverted Index) хранит инвертированный список: `триграмма → {строки, содержащие эту триграмму}`. При запросе `LIKE '%guitar%'`:

1. Паттерн `guitar` разбивается: `{"gui", "uit", "ita", "tar"}`
2. GIN ищет пересечение списков строк по всем четырём триграммам
3. Кандидаты проверяются финальным heap-fetch (устраняются false positives)
4. Результат — только строки, реально содержащие подстроку

Для паттернов короче 3 символов (1-2 буквы) триграммный индекс не применяется — слишком много кандидатов. Для паттернов ≥ 3 символов GIN даёт Index Scan.
