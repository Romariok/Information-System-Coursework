# Архитектурные решения и компромиссы

## Почему PostgreSQL, а не что-то другое

MongoDB была очевидным кандидатом — данные о продуктах хорошо легли бы в документы, enum-атрибуты не пришлось бы городить. Но мы остановились на реляционной БД.

Главное — связность данных. Продукт связан с музыкантами, магазинами, статьями, отзывами, пользователями. С Mongo пришлось бы либо денормализовывать всё, либо делать $lookup, что не лучше JOIN-а. Плюс транзакции: когда пишем отзыв, рейтинг должен обновиться атомарно.

## JWT без хранилища: что теряем

Stateless JWT не позволяет мгновенно отозвать токен. Если пользователь сменил пароль или вышел, старый токен работает до истечения TTL. Мы выбрали короткий TTL (1 час) — для сервиса подбора гитар, где нет ничего критически чувствительного, это нормально. Финансовые операции потребовали бы blacklist в Redis.

Зато без общего хранилища сессий. Стандартный выбор для API за балансировщиком.

## Денормализованные счётчики: осознанный write overhead

Средний рейтинг, средняя цена и количество подписчиков хранятся прямо в строке сущности, не вычисляются при каждом чтении. За это платим тем, что каждый INSERT/UPDATE/DELETE на `feedback` или `shop_product` запускает триггер.

Пошли на это потому, что чтение происходит на порядки чаще записи. `GET /api/product/filter` должен быстро сортировать по рейтингу — подзапрос с AVG() убивал бы любой индекс. Отзывы добавляют редко. Если read/write ratio больше 10:1, денормализация обычно оправдана.

## TTL кэша: почему 60 секунд, а не больше

Казалось бы, поставь TTL на 10 минут — нагрузка упадёт ещё сильнее. Но тогда модератор принял статью, а пользователь ещё несколько минут видит её в списке «не принятых». Администратор добавил музыканта, а он появляется на странице только через 10 минут.

60 секунд — компромисс между попаданием в кэш и допустимой задержкой. Для контента, где свежесть не критична (список брендов, характеристики продукта), можно поставить и больше. Для того, что меняется часто, кэш-инвалидация через `@CacheEvict` точечная.

## Specification Pattern для фильтрации

Фильтр продуктов принимает до 10+ параметров: тип, форма корпуса, материал, цвет, диапазон цены, диапазон рейтинга, количество ладов, строй — все опциональные.

Варианты: 1) строить JPQL-строку вручную — сложно, опасно SQL-инъекциями; 2) написать 20+ разных методов в репозитории — комбинаторный взрыв; 3) Specification API — каждый фильтр это отдельный предикат, компонуются через `and()`.

Specification — стандартный ответ Spring Data на «нужна динамическая фильтрация». QueryDSL или Criteria API тоже работают, но Specification встроен, и для нашей задачи достаточен.

## Haskell-парсер Markdown

Самое нестандартное решение в проекте. Парсер Markdown — отдельный бинарник, скомпилированный из Haskell, запускается через `ProcessBuilder`. Для Java-приложения звучит странно.

История простая: Haskell-парсер был уже ранее разработан в рамках предмета «Функциональное программирование» — интегрировали как внешний инструмент. Минус стал виден при профилировании — 20 статей на страницу = 20 форков процесса. Решение: вычислять HTML один раз при сохранении, хранить в `html_content`, при чтении брать готовое.

## @Async для тяжёлых операций

При добавлении нового музыканта нужно обработать и связать данные. Делать это синхронно — пользователь ждёт работу, которую можно отложить. `@Async` возвращает ответ сразу, тяжёлую работу выполняет в пуле потоков.

Риск: если сервер упадёт в момент выполнения async-задачи, работа потеряется. Для нашего сценария это приемлемо — данные не критические. Для чего-то важного нужна очередь сообщений с гарантией доставки.
