# Надёжность и ограничения

## Как думали про надёжность

Надёжность здесь — это предсказуемость: система ведёт себя одинаково при нормальной нагрузке и при всплесках, не теряет данные при рестарте, запускается в воспроизводимом состоянии.

`backend` ждёт, пока PostgreSQL пройдёт `pg_isready`. Без этого Spring Boot при старте пытался подключиться к ещё не готовой базе и падал. `redis` healthcheck не нужен — драйвер переподключается сам, а кэш не источник истины, его потеря не ломает систему.

Схема базы меняется через Flyway, не руками. Если откатиться на предыдущую версию контейнера — схема и код согласованы.

У postgres и backend явно заданы CPU и RAM в Compose. Без лимитов один контейнер может исчерпать ресурсы хоста и положить остальных. Redis запущен с `appendonly yes` — кэш восстановится после рестарта контейнера. `logback-spring.xml` с ротацией файлов, уровни логирования через переменные окружения — SQL-трейс можно включить без пересборки образа.

## Что намеренно не делали

Retry и circuit breaker не добавляли. Для монолита с одной БД и одним Redis это избыточно — circuit breaker нужен, когда есть внешние вызовы с нестабильным SLA. Добавлять «на вырост» значит усложнять без причины.

Один Postgres-инстанс, без репликации. Read replica сняла бы нагрузку с SELECT-запросов фильтрации, но Redis кэш уже закрывает большую часть повторных чтений. Для нашего масштаба достаточно.

`@Async` вместо Kafka/RabbitMQ — задачи, которые сейчас асинхронные, некритические. Потеря одной не ломает состояние системы.

## Где может сломаться

Если PostgreSQL лег — всё встало, альтернативного пути нет. Если Redis лег — кэш инвалидируется, нагрузка на БД вырастет, сервис продолжит работать. Если async-задача упала при рестарте — данные могут быть частично обновлены. Известные компромиссы для данного масштаба.
