# Оптимизация

## Как искали проблемы

Сначала 7 минут заполняли БД тестовыми данными, затем смотрели p95 в Prometheus:

```promql
topk(10,
  histogram_quantile(
    0.95,
    sum by (uri, le) (
      http_server_requests_seconds_bucket{uri!~"/actuator/.*"}
    )
  )
)
```

Выяснилось, что авторизация работала в 4 раза медленнее любого фильтра по продуктам. Три проблемных эндпоинта: музыканты, авторизация, статьи.

## N+1 у музыкантов

`MusicianService.getMusician` загружал страницу музыкантов, а потом для каждого делал три отдельных запроса к `musician_genre`, `type_of_musician_musician` и `musician_product` — итого `1 + 3×N` запросов на страницу.

Переписали на batch-запросы: добавили `findByMusicianIdIn(List<Long> ids)` в репозитории, в сервисе — метод `buildMusicianInfoDTOs`, который собирает все `musician_id` со страницы, одним запросом тянет жанры/типы/продукты для всех, группирует по `Map<id, List<...>>` и собирает DTO. Теперь всегда 4 запроса независимо от размера страницы, время ответа упало больше чем в 2 раза.

## Markdown в hot path

`ArticleService` при каждом запросе списка статей конвертировал Markdown в HTML через `ProcessBuilder` — для каждой статьи отдельно. При 20 статьях на страницу — 20 форков процесса.

Добавили колонку `html_content TEXT` в таблицу `articles`. HTML вычисляется один раз при создании и сохраняется. При чтении просто берём готовое поле. Заодно убрали N+1 по авторам через `@EntityGraph(attributePaths = "author")`. p95 для `/api/article` снизился с 0.13 с до 0.03 с.

## Дублирующий SELECT при логине

При рефакторинге нашли лишний SELECT: при логине сначала вызывался `userRepository.findByUsername(...)`, а потом `authenticationManager.authenticate(...)` снова загружал того же пользователя через `UserDetailsService`. Убрали первый вызов, берём пользователя из `authentication.getPrincipal()`.

## Результат

После всех трёх правок среднее время ответа по REST-ручкам снизилось в 2.5–3 раза.
