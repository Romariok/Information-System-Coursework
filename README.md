# GMatch — сервис подбора гитар

Курсовая по «Информационным системам», ИТМО, группа P3312. Авторы: Кобелев Роман, Балин Артём.

---

## Что это

Выбрать гитару сложно: параметров куча, мнения расходятся, и непонятно, что реально играет твой любимый музыкант. GMatch пытается это исправить — ищешь по характеристикам (тип, форма, материал, цвет, цена, рейтинг), видишь список gear конкретного исполнителя, читаешь и пишешь обзоры прямо на странице продукта, подписываешься на музыкантов.

## Архитектура

### Слои

Бэкенд разбит на `controller → service → repository`. Бизнес-логика не живёт в контроллерах — это конкретно помогло, когда пришлось переписывать запросы при оптимизациях: сервисный слой трогали изолированно.

### Аутентификация

Stateless JWT вместо сессий — нет общего хранилища, проще масштабировать. Секрет, TTL токена и сила BCrypt вынесены в переменные окружения. В docker-окружении ставим `BCRYPT_STRENGTH=8`, в проде по умолчанию 10.

При рефакторинге нашли лишний SELECT: при логине сначала вызывался `userRepository.findByUsername(...)`, а потом `authenticationManager.authenticate(...)` снова загружал того же пользователя через `UserDetailsService`. Убрали первый вызов, берём пользователя из `authentication.getPrincipal()`.

### WebSocket

Уведомления о новых отзывах и статьях идут через Spring WebSocket + STOMP. Топики (`/feedbacks`, `/articles`) и допустимые origins в конфигурации. Парсер данных вынесен в `@Async`-задачи — HTTP-поток не блокируется при добавлении новых исполнителей.

### Кэширование

Часто запрашиваемые списки (бренды, продукты, музыканты) кэшируются в Redis. Сериализация настроена с `JavaTimeModule` под Java 8 date/time, TTL и префикс ключей берутся из `application.properties`.

## Архитектурные решения и компромиссы

### Почему PostgreSQL, а не что-то другое

MongoDB была очевидным кандидатом — данные о продуктах хорошо легли бы в документы, enum-атрибуты не пришлось бы городить. Но мы остановились на реляционной БД.

Главное — связность данных. Продукт связан с музыкантами, магазинами, статьями, отзывами, пользователями. С Mongo пришлось бы либо денормализовывать всё, либо делать $lookup, что не лучше JOIN-а. Плюс транзакции: когда пишем отзыв, рейтинг должен обновиться атомарно.

### JWT без хранилища: что теряем

Stateless JWT не позволяет мгновенно отозвать токен. Если пользователь сменил пароль или вышел, старый токен работает до истечения TTL. Мы выбрали короткий TTL (1 час) — для сервиса подбора гитар, где нет ничего критически чувствительного, это нормально. Финансовые операции потребовали бы blacklist в Redis.

Зато без общего хранилища сессий. Стандартный выбор для API за балансировщиком.

### Денормализованные счётчики: осознанный write overhead

Средний рейтинг, средняя цена и количество подписчиков хранятся прямо в строке сущности, не вычисляются при каждом чтении. За это платим тем, что каждый INSERT/UPDATE/DELETE на `feedback` или `shop_product` запускает триггер.

Пошли на это потому, что чтение происходит на порядки чаще записи. `GET /api/product/filter` должен быстро сортировать по рейтингу — подзапрос с AVG() убивал бы любой индекс. Отзывы добавляют редко. Если read/write ratio больше 10:1, денормализация обычно оправдана.

### TTL кэша: почему 60 секунд, а не больше

Казалось бы, поставь TTL на 10 минут — нагрузка упадёт ещё сильнее. Но тогда модератор принял статью, а пользователь ещё несколько минут видит её в списке «не принятых». Администратор добавил музыканта, а он появляется на странице только через 10 минут.

60 секунд — компромисс между попаданием в кэш и допустимой задержкой. Для контента, где свежесть не критична (список брендов, характеристики продукта), можно поставить и больше. Для того, что меняется часто, кэш-инвалидация через `@CacheEvict` точечная.

### Specification Pattern для фильтрации

Фильтр продуктов принимает до 10+ параметров: тип, форма корпуса, материал, цвет, диапазон цены, диапазон рейтинга, количество ладов, строй — все опциональные.

Варианты: 1) строить JPQL-строку вручную — сложно, опасно SQL-инъекциями; 2) написать 20+ разных методов в репозитории — комбинаторный взрыв; 3) Specification API — каждый фильтр это отдельный предикат, компонуются через `and()`.

Specification — стандартный ответ Spring Data на «нужна динамическая фильтрация». QueryDSL или Criteria API тоже работают, но Specification встроен, и для нашей задачи достаточен.

### Haskell-парсер Markdown

Самое нестандартное решение в проекте. Парсер Markdown — отдельный бинарник, скомпилированный из Haskell, запускается через `ProcessBuilder`. Для Java-приложения звучит странно.

История простая: Haskell-парсер был уже ранее разработан в рамках предмета "Функциональное программирование" - интегрировали как внешний инструмент. Минус стал виден при профилировании — 20 статей на страницу = 20 форков процесса. Решение: вычислять HTML один раз при сохранении, хранить в `html_content`, при чтении брать готовое.

### @Async для тяжёлых операций

При добавлении нового музыканта нужно обработать и связать данные. Делать это синхронно — пользователь ждёт работу, которую можно отложить. `@Async` возвращает ответ сразу, тяжёлую работу выполняет в пуле потоков.

Риск: если сервер упадёт в момент выполнения async-задачи, работа потеряется. Для нашего сценария это приемлемо — данные не критические. Для чего-то важного нужна очередь сообщений с гарантией доставки.

## База данных

### Модель

10 основных сущностей плюс junction-таблицы для many-to-many:

- `product` — гитара, усилитель, педаль и т.д., 12+ enum-атрибутов
- `musician` — музыкант с жанрами, типами игры и списком оборудования
- `app_user` — пользователь с ролями и подписками
- `shop` / `shop_product` — магазины и цены на конкретный продукт
- `articles` / `feedback` — статьи и отзывы с модерацией
- `forum_topic` / `forum_post` — форум

Ссылочная целостность: `ON DELETE CASCADE` там, где дочерние записи без родителя теряют смысл; `ON DELETE SET NULL` там, где запись можно оставить (например, отзыв без автора).

### Триггеры

Средний рейтинг, средняя цена и счётчики подписок хранятся денормализованно прямо в строке сущности и поддерживаются триггерами:

| Триггер | Событие | Что обновляет |
|---|---|---|
| `update_product_rating` | INSERT/UPDATE/DELETE на `feedback` | `product.rate` |
| `update_product_average_price` | INSERT/UPDATE/DELETE на `shop_product` | `product.avg_price` |
| `update_user_subscriptions` | INSERT/DELETE на `user_musician_subscription` | `app_user.subscriptions` |
| `update_musician_subscribers` | INSERT/DELETE на `user_musician_subscription` | `musician.subscribers` |

Небольшой write-overhead, зато фильтрация не требует агрегирующих JOIN-ов при каждом чтении.

### Хранимые процедуры

- добавление отзыва с обновлением рейтинга
- подписка на музыканта
- модерация статей

### Индексы

Индексы создавались после профилирования, не наугад. Покрыли FK-колонки, поля фильтрации (`type_of_product`, `guitar_form`, `rate`, `avg_price`, `stars`), поля поиска (`name`, `header`, `title`) и составные индексы для частых паттернов: `(musician_id, genre)`, `(shop_id, price)`, `(author_id, product_id, article_id)`.

Самый заметный результат — фильтрация продуктов по типу + цвету + цене + рейтингу:

```
Было:  73.7 мс
Стало:  2.0 мс
```

## Надёжность и ограничения

### Как думали про надёжность

Надёжность здесь — это предсказуемость: система ведёт себя одинаково при нормальной нагрузке и при всплесках, не теряет данные при рестарте, запускается в воспроизводимом состоянии.

`backend` ждёт, пока PostgreSQL пройдёт `pg_isready`. Без этого Spring Boot при старте пытался подключиться к ещё не готовой базе и падал. `redis` healthcheck не нужен — драйвер переподключается сам, а кэш не источник истины, его потеря не ломает систему.

Схема базы меняется через Flyway, не руками. Если откатиться на предыдущую версию контейнера — схема и код согласованы.

У postgres и backend явно заданы CPU и RAM в Compose. Без лимитов один контейнер может исчерпать ресурсы хоста и положить остальных. Redis запущен с `appendonly yes` — кэш восстановится после рестарта контейнера. `logback-spring.xml` с ротацией файлов, уровни логирования через переменные окружения — SQL-трейс можно включить без пересборки образа.

### Что намеренно не делали

Retry и circuit breaker не добавляли. Для монолита с одной БД и одним Redis это избыточно — circuit breaker нужен, когда есть внешние вызовы с нестабильным SLA. Добавлять «на вырост» значит усложнять без причины.

Один Postgres-инстанс, без репликации. Read replica сняла бы нагрузку с SELECT-запросов фильтрации, но Redis кэш уже закрывает большую часть повторных чтений. Для нашего масштаба достаточно.

`@Async` вместо Kafka/RabbitMQ — задачи, которые сейчас асинхронные, некритические. Потеря одной не ломает состояние системы.

### Где может сломаться

Если PostgreSQL лег — всё встало, альтернативного пути нет. Если Redis лег — кэш инвалидируется, нагрузка на БД вырастет, сервис продолжит работать. Если async-задача упала при рестарте — данные могут быть частично обновлены. Известные компромиссы для данного масштаба.

## Оптимизация

### Как искали проблемы

Сначала 7 минут заполняли БД тестовыми данными, затем смотрели p95 в Prometheus:

```promql
topk(10,
  histogram_quantile(
    0.95,
    sum by (uri, le) (
      http_server_requests_seconds_bucket{uri!~"/actuator/.*"}
    )
  )
)
```

Выяснилось, что авторизация работала в 4 раза медленнее любого фильтра по продуктам. Три проблемных эндпоинта: музыканты, авторизация, статьи.

### N+1 у музыкантов

`MusicianService.getMusician` загружал страницу музыкантов, а потом для каждого делал три отдельных запроса к `musician_genre`, `type_of_musician_musician` и `musician_product` — итого `1 + 3×N` запросов на страницу.

Переписали на batch-запросы: добавили `findByMusicianIdIn(List<Long> ids)` в репозитории, в сервисе — метод `buildMusicianInfoDTOs`, который собирает все `musician_id` со страницы, одним запросом тянет жанры/типы/продукты для всех, группирует по `Map<id, List<...>>` и собирает DTO. Теперь всегда 4 запроса независимо от размера страницы, время ответа упало больше чем в 2 раза.

### Markdown в hot path

`ArticleService` при каждом запросе списка статей конвертировал Markdown в HTML через `ProcessBuilder` — для каждой статьи отдельно. При 20 статьях на страницу — 20 форков процесса.

Добавили колонку `html_content TEXT` в таблицу `articles`. HTML вычисляется один раз при создании и сохраняется. При чтении просто берём готовое поле. Заодно убрали N+1 по авторам через `@EntityGraph(attributePaths = "author")`. p95 для `/api/article` снизился с 0.13 с до 0.03 с.

### Дублирующий SELECT при логине

Описано выше в разделе про аутентификацию.

После всех трёх правок среднее время ответа по REST-ручкам снизилось в 2.5–3 раза.

## CI/CD

Три workflow в GitHub Actions:

`ci.yml` — на каждый push и PR в `main`/`release`. Собирает бэкенд (`mvn package -DskipTests`, JDK 17 Temurin), ставит зависимости фронтенда, прогоняет ESLint + Prettier и сборку, потом собирает Docker-образы без пуша — просто проверяем, что Dockerfile-ы не сломаны.

`release.yml` — на теги `v*` и push в `main`/`release`. Пушит образы в GHCR, экспортирует их в `.tar.gz` и создаёт GitHub Release с архивами и автогенерированными release notes.

`vulnerabilities.yml` — статический анализ: SpotBugs через `mvn verify` и Snyk по `pom.xml`. Оба отчёта сохраняются как артефакты. Dependabot в дополнение — сам открывает PR при обновлениях зависимостей в `pom.xml` и `package.json`.

### Docker

Всё поднимается одной командой:

```bash
cd .docker && docker compose up -d
```

Сервисы: `postgres`, `pgadmin`, `backend`, `frontend`, `redis`, `prometheus`, `grafana`, `cadvisor`. Postgres поднимается с health check (`pg_isready`), остальные ждут его. Ресурсные лимиты заданы явно. Инициализационные SQL монтируются через `docker-entrypoint-initdb.d`.

Backend собирается в multi-stage Dockerfile: первый stage компилирует Haskell-парсер, второй собирает Maven-артефакт, третий — минимальный JRE-образ для запуска. Frontend: Node для сборки Vite, Nginx для раздачи статики.

### Мониторинг

Бэкенд отдаёт метрики через `/actuator/prometheus`, Prometheus их собирает, cAdvisor добавляет метрики контейнеров (CPU, RAM, сеть, диск). Grafana поднимается с уже настроенными datasource и дашбордами через provisioning — руками ничего настраивать не нужно.

Из полезного: `http_server_requests_seconds_bucket` для гистограммы по эндпоинтам, `jvm_memory_used_bytes` и `hikaricp_connections_active` для понимания состояния приложения.

## API

| Контроллер | Основные операции |
|---|---|
| `AuthController` | POST /api/auth/register, /api/auth/login |
| `ProductController` | GET /api/product/filter (многокритериальный), /api/product/type/{type}, /api/product/{name} |

## Запуск

```bash
cd .docker
docker compose up -d

# Backend:    http://localhost:5252
# Frontend:   http://localhost:5173
# Grafana:    http://localhost:3000  (admin/admin)
# Prometheus: http://localhost:9090
# PgAdmin:    http://localhost:5050
```

Бэкенд без Docker (нужен запущенный postgres):

```bash
export POSTGRES_NAME=postgres POSTGRES_USER=postgres POSTGRES_PASSWORD=pgpwd
export PORT=5252 JWT_SECRET=your-secret JWT_EXPIRATION_MS=3600000

mvn -f backend/pom.xml spring-boot:run
```
